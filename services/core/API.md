# Authenticated local core API

Implemented 2026-10-14. This API wraps the durable core; it does not yet dispatch coding commands or connect the legacy assistant. It accepts native local clients only. Mobile access needs a separately authenticated remote gateway later.

## Credentials and roles

All routes, including health, require an `Authorization: Bearer <token>` header. Use independently generated high-entropy tokens, for example `secrets.token_urlsafe(32)`. Raw tokens belong in protected client storage and must never be included in model context. The server registry contains their SHA-256 digests, not their original values.

The authenticated registry determines actor and role; request bodies cannot select or override them. Each project currently has one owner. Agent and worker credentials represent delegated access for that owner and must name exact project IDs. This is not employee role management or a multi-tenant identity provider.

| Role | Allowed responsibilities |
|---|---|
| Controller | Create projects; change policy; review/decide approvals; cancel, recover and reconcile tasks; inspect owned state. Keep this credential out of agents/workers. |
| Agent | Read assigned project state; create task intents and conversations; append assistant/tool messages. Cannot approve, widen scope, impersonate a user, claim or complete work. |
| Worker | Inspect assigned tasks/events; claim approved work; heartbeat and record results using its lease token. Cannot approve, change policy or reconcile uncertain work. |

Registry entries use this structure; replace the digest with the hash of a securely generated token:

```json
[
  {
    "token_sha256": "<64 lowercase hexadecimal SHA-256 characters>",
    "actor": "local-owner",
    "role": "controller",
    "projects": []
  }
]
```

Provision the controller first, create a project, then configure separate agent/worker credentials with that project ID. Registry changes take effect after restart. Revoking a token in the registry requires restarting this slice. Restrict registry file writes to the owning OS account: replacing a digest is equivalent to granting access. Credential provisioning and OS credential-store integration will be part of desktop integration; no permanent credentials were generated by this phase.

## Developer launch

From the Jarvis repository root, using its existing Python environment:

```powershell
.\venv\Scripts\python.exe services/core/run.py --auth-config C:\path\to\private-registry.json
```

This developer launcher binds only to `127.0.0.1:8010`, disables proxy-header trust and request access logs, and limits concurrent connections. It does not accept raw credentials on the command line. Default state lives at `%LOCALAPPDATA%\Skyra\Jarvis\core.sqlite3`; `--database` may override this explicitly for development. Do not use a shared/network SQLite file or a synced project folder for real runtime state.

This command is for development. Hidden Windows process supervision and a desktop launcher remain follow-up work. No service is left running by the test suite.

Direct dependency pins are in [requirements-api.txt](requirements-api.txt); test dependencies are in [requirements-test.txt](requirements-test.txt). They match the already-installed environment used for verification and are not a complete transitive lock. No package installations or upgrades were performed in this phase.

## Implemented routes

File-worker update: an optional trusted adapter adds `POST /v1/tasks/{task}/perform` (worker-only, valid lease required) and `GET /v1/tasks/{task}/evidence/{checksum}` (controller/assigned agent, attached evidence only). The default API has no adapter and returns unavailable for these operations. See the [file-worker implementation](../../workers/coding/IMPLEMENTATION.md) and launch with `--workspace-config` only after preparing and protecting that registry. The API does not accept filesystem registrations from agent payloads.

| Surface | Behavior |
|---|---|
| `GET /v1/health` | Authenticated local readiness response after successful initialization. |
| `GET /v1/openapi.json` | Controller-only generated contract. Public Swagger/Redoc routes are disabled. |
| `POST /v1/projects`, `GET /v1/projects` | Create/list owned projects; delegated listings are filtered by assigned project IDs. |
| `PUT /v1/projects/{project}/policy` | Controller sets `read_only`, `ask` or scoped `full`, with explicit resource IDs. |
| `POST /v1/projects/{project}/conversations` | Create a conversation in the allowed project. |
| `POST/GET /v1/conversations/{conversation}/messages` | Insert or replay messages; insertion requires a request ID. |
| `POST /v1/projects/{project}/tasks` | Create an immutable task intent with action, resource, payload and required request ID. |
| `GET /v1/tasks/{task}` | Read task state, with lease token removed. |
| `POST /v1/tasks/{task}/start` | Worker receives approval-wait state or an exclusive lease. Does not execute the task. |
| `POST /v1/tasks/{task}/heartbeat`, `/complete` | Worker must supply its valid lease token. Completion records evidence references. |
| `POST /v1/tasks/{task}/cancel` | Controller records cancellation; running effects remain uncertain until confirmed. |
| `GET /v1/approvals/{approval}` | Controller inspects exact task, digest, expiry and policy version. |
| `POST /v1/approvals/{approval}/decision` | Controller approves/rejects an exact pending action. Strict boolean required. |
| `POST /v1/projects/{project}/recover` | Controller marks expired work as interrupted/uncertain. |
| `POST /v1/tasks/{task}/reconcile` | Controller records an independently verified outcome before retry or closure. |
| `GET /v1/projects/{project}/events` | Bounded event replay using `after` cursor and `limit` (1–200). Message replay uses the same pagination convention. |

Request schemas reject unknown fields and coerced values. Task/message retries with the same request ID return the original result; changed content is a conflict. Project/conversation creation does not yet have idempotency keys, so clients must not automatically retry those creations after an unknown outcome. No live streaming or worker scheduler is implemented yet.

## Request boundary

- Authenticate before accepting request bodies; reject remote client addresses, untrusted Host headers and duplicate authorization headers.
- Reject browser Origin/fetch requests. No CORS access is enabled; a future desktop native bridge should own privileged requests.
- Accept bounded JSON bodies only, including streamed bodies; reject duplicate JSON keys, malformed JSON and nonstandard constants. Enforce a ten-second body-read deadline.
- Return sanitized error codes and server-generated request IDs; do not echo submitted data or storage exception details. Responses use `no-store` and `nosniff`.
- Project ownership and delegated project scope are both checked. Full-access policy still requires an explicit resource ID.

Loopback authentication is a local boundary, not protection against compromise of the same OS account. Resource IDs are logical scopes; filesystem/process isolation must be enforced by the execution adapter. Evidence references are recorded, not independently validated by this API. Do not expose this endpoint to the Internet or connect autonomous command execution before the worker boundary is implemented.

## Verification and limits

The suite uses real temporary SQLite state and FastAPI's in-process request client. It covers controller/agent/worker separation, tenant/actor denial, approval changes, duplicate request handling after app restart, malformed/oversized requests, host/origin rejection, token hiding and schema protection. No live network listener, model provider, browser or external system is contacted by these tests.

The existing environment emits a Starlette warning that HTTPX-based TestClient is deprecated. The suite passes with the installed versions. Test-client migration and a full transitive dependency lock are follow-up tooling work, not hidden by warning suppression.
